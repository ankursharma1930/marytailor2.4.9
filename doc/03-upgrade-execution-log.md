# 2.4.9 upgrade — execution log

What actually happened, in order, and the two faults that stopped it. Follows
the plan in `02-upgrade-plan.md`; deviations from it are called out.

**Outcome: `bin/magento --version` reports 2.4.9, `setup:db:status` reports all
modules up to date, storefront and admin both return HTTP 200.**

## Deviation from the plan — no database backup was taken

`shell/03-backup.sh` was never run. At the time of writing there is no
`.sql.gz` anywhere on disk and `/var/backups/marytylor-2.4.9/` does not exist.

The code side is covered — the `pre-2.4.9-upgrade` git branch exists — but
**stage 5 of the plan rewrote the schema against live data with no DB safety
net**, and `02-upgrade-plan.md` is explicit that a stage-5 failure always
means a DB restore. That option was never available. 10,470 orders and 5,003
customers were exposed for the duration.

This cannot be retrofitted; the pre-upgrade state is gone. Take one before any
further schema work:

```bash
bash shell/db-backup.sh     # ~1.74 GB, 141 GB free
```

## Fault 1 — `setup:upgrade` aborted in Magento_Fedex

```
vendor/magento/module-fedex/Setup/Patch/Data/UpdateFedexInternationalPriority.php:50
explode(): Argument #2 ($string) must be of type string, null given
```

**Cause.** The patch rewrites the `INTERNATIONAL_PRIORITY` method code to
`FEDEX_INTERNATIONAL_PRIORITY`. It reads every `core_config_data` row for
`carriers/fedex/allowed_methods` and `carriers/fedex/free_method` and calls
`explode(',', $row['value'])` with no NULL guard. This database stores
`carriers/fedex/free_method` as NULL, and the patch declares
`strict_types=1` — so NULL is not coerced to `''` and PHP raises a TypeError.
Upstream bug: the column is nullable, the patch assumes it is not.

The patch had real work to do — `allowed_methods` did contain
`INTERNATIONAL_PRIORITY` — so skipping it was not an option.

**Fix.** `shell/fix-null-config-for-data-patches.php --apply` — sets the NULL
to `''`, which is what NULL already meant for that field.

**Deleting the row would have been wrong.** `module-fedex/etc/config.xml`
defines a default of `FEDEX_GROUND`, so falling back to the default would have
silently switched on FedEx Ground as a free shipping method.

Rollback SQL: `var/backups/core_config_data-null-fix-20260912-141002.sql`.

Checked for recurrence before re-running: this DB holds **471** NULL config
rows, but only this one blocks. Of the other 2.4.9 data patches that
`explode()` near `core_config_data`, `module-config RemoveTinymceConfig` does
not explode the value, and `module-paypal UpdateBmltoPayLater` explodes the
config *path*, which is `NOT NULL`. The other 470 NULLs were deliberately left
alone — NULL and `''` differ wherever code distinguishes them, and that is not
a change to make blind across a live config table.

## Fault 2 — `Cannot instantiate interface Magento\Csp\Model\Collector\MergerInterface`

Appeared after `setup:upgrade` completed.

**Cause.** `Magento_Csp` was disabled. The preference lives in the module's own
config, so a disabled module means the mapping never reaches compiled DI:

```xml
<!-- vendor/magento/module-csp/etc/di.xml:18 -->
<preference for="Magento\Csp\Model\Collector\MergerInterface"
            type="Magento\Csp\Model\Collector\CompositeMerger" />
```

Meanwhile `Magento_Csp`'s own `CompositePolicyCollector` still gets
instantiated, because **`Magento_Checkout`, `Magento_Theme`, `Magento_Paypal`
and `Magento_AdminAnalytics` all declare `magento/module-csp` as a hard
composer dependency in 2.4.9.** Running 2.4.9 with it disabled is not viable.

It was already disabled before this upgrade — `git show HEAD:app/etc/config.php`
has `'Magento_Csp' => 0`. Survivable on 2.4.6, not on 2.4.9.

**Fix.** Enable the module, then recompile. Safe to leave on: CSP ships
`report_only = 1` for both storefront and admin, so it reports violations
rather than blocking scripts — which matters on a Hyvä storefront carrying
this many third-party modules.

```bash
php bin/magento module:enable Magento_Csp
```

The error persisted after enabling because `generated/` had been compiled
*before* the module was switched on, and **production mode never regenerates
DI on demand** — the recompile below is what actually cleared it.

## Post-upgrade rebuild

Run under maintenance mode, as the code owner (`payless`, never root — root
ownership in `generated/` locks out later CLI runs):

```bash
php bin/magento maintenance:enable
php bin/magento setup:di:compile
php bin/magento setup:static-content:deploy -f
php bin/magento cache:flush
php bin/magento maintenance:disable
```

Static content predated the upgrade and had to be redeployed;
`deployed_version.txt` moved `1789211733` → `1789223004`.

**`pub/static/.htaccess` must be checked after every static deploy.** It ships
in the distribution, is not regenerated by `static-content:deploy`, and is not
in this repo's git index — see `00-local-environment-setup.md`, fault 1. If it
goes missing the storefront loads unstyled with 404s on every asset.

## Fault 3 — frontend regressions from the Hyvä theme jump

Reported as "so many errors in console and UI got broke". Three separate
causes, none of them CSP. For the record, CSP is **not** implicated: only
`Content-Security-Policy-Report-Only` is sent, never an enforcing header, so
it blocks nothing. It does make the console noisy, because report-only
violations still log — but it is not what broke anything.

**The composer upgrade moved Hyvä 1.3.9 → 1.5.2.** `CLAUDE.md` records 1.3.9;
`composer.lock` now pins `hyva-themes/magento2-default-theme 1.5.2`. Two
minor versions of the frontend theme, which is the root of all three.

### 3a. Font Awesome disappeared — every icon on the site

The stylesheet was injected by a one-line template:

```
vendor/mirasvit/module-core/src/Core/view/frontend/templates/font_awesome.phtml
  <link rel="stylesheet" ... href="https://maxcdn.bootstrapcdn.com/font-awesome/latest/css/font-awesome.min.css">
```

registered by that module's own `view/frontend/layout/default.xml`. The
upgrade moved `mirasvit/module-core` to 1.7.20, **which dropped the template**
— its templates directory now holds only `custom_css.phtml`. The `<link>`
silently vanished from every page.

**Fixed** by declaring the stylesheet in the child theme instead, at
`app/design/frontend/Aureate/hyva/Magento_Theme/layout/default.xml`. In the
child theme, not `vendor/` — this is the exact failure mode `CLAUDE.md` warns
about, and a vendor edit would be destroyed by the next update. The CDN URL
was confirmed live (HTTP 200, 31 KB) before restoring it, and
`maxcdn.bootstrapcdn.com` is already permitted by the CSP `style-src` and
`font-src` directives, so no `csp_whitelist.xml` change was needed.

### 3b. 171 KB of duplicated inline JS — the console errors

Homepage inline JavaScript went from 135,732 to 309,694 bytes. Effectively all
of the increase is Mirasvit Rewards "points block" scripts:

| | pre-upgrade | now |
|---|---|---|
| `initPointsBlock*` script tags | **0** | **8** |
| bytes | 0 | **170,912** |

Four block ids (37, 38, 39, 56), each emitted **twice**. The source is a price
adjustment renderer:

```
vendor/mirasvit/module-rewards-hyva/src/MirasvitRewardsCatalog/view/frontend/templates/pricing/adjustment.phtml
```

Being a price-adjustment renderer, it fires **once per rendered product
price** — twice per product, for regular and final price — and each emission
carries a full ~21 KB copy of the same function. It rendered zero times before
the upgrade, so the Hyvä integration layouts (`hyva_*` handles) were dormant
under 1.3.9 and are now active under 1.5.2, which also newly installs
`Hyva_BaseLayoutReset` (`magento2-base-layout-reset 2.0.5`) and adds
`<update handle="default_hyva"/>` to the theme's `default.xml`.

**Not fixed — needs a decision.** Suppressing it is a business choice, since
it removes the per-product points display:

```
rewards/display_options/is_show_points_on_frontend      = 1
rewards/display_options/is_show_points_on_product_page  = 1
```

The better outcome is for the duplication to be fixed rather than the feature
switched off; this is a Mirasvit integration defect worth raising with them,
given the licence is paid.

### 3c. The real cause of the broken header/homepage/category: stale Tailwind CSS

Hyvä's CSS is a **purged** Tailwind build — it contains only the utility classes
found by scanning the templates at build time. `styles.css` was byte-identical
to the pre-upgrade backup, i.e. **it was never rebuilt for 1.5.2**. So every
class that only 1.5.2's markup emits had no rule at all. That is why three
different page types broke at once: the stylesheet no longer matched the
templates.

The worst case was `md:inline-flex`. 1.5.2's header icons are
`hidden md:inline-flex`; with no rule for the responsive variant they simply
**stayed hidden**.

**Fixed:**

```bash
cd app/design/frontend/Aureate/hyva/web/tailwind
npm ci          # node_modules was broken: the tailwindcss bin could not
                # resolve './cli/index', so the build failed outright
npm run build   # 169,745 B unminified -> 135,433 B minified
```

`tailwind.config.js` already globbed the vendor parent theme
(`vendor/hyva-themes/magento2-default-theme/**/*.phtml`), so the rebuild picked
up 1.5.2's markup without config changes.

**Rebuild the CSS after any Hyvä version change.** Nothing in the Magento
upgrade does it, and the failure is silent — no error anywhere, just unstyled
and invisible elements.

### 3d. Upstream Hyvä bug: `lg:order-0` can never be generated

`Magento_Theme/templates/html/header.phtml` lines 102 and 109 use
`lg:order-0`, but Tailwind v3 ships no `order-0` utility — its zero is
`order-none` — and Hyvä's own reference config
(`magento2-theme-module/src/view/frontend/tailwind/tailwind.config.js`) does
not define one either. The class is therefore unreachable, leaving the logo
wrapper and the header icon group stuck at `order-1` on desktop.

Worked around in the child theme's `tailwind.config.js`:

```js
extend: { order: { '0': '0' } }
```

### 3e. `setup:static-content:deploy -f` does not overwrite deployed files

This cost a wasted deploy cycle and is worth remembering. After rebuilding the
CSS, a full `setup:static-content:deploy -f` **bumped `deployed_version.txt`
and wrote only 17 files**, leaving `pub/static/.../css/styles.css` at its old
169,745 bytes. `-f` forces deployment to *run*; it does not force existing
files to be replaced.

What actually works:

```bash
rm -rf var/view_preprocessed/* pub/static/frontend/Aureate/hyva
php bin/magento setup:static-content:deploy -f --theme Aureate/hyva en_US
```

`pub/static/.htaccess` sits one level above the theme directory, so it survives
this — but check it anyway (see `00-local-environment-setup.md`, fault 1).

### 3f. Mixed file ownership in var/cache broke the homepage with a 500

Immediately after the redeploy the homepage returned HTTP 500:

```
RuntimeException: Failed to write tag file: var/cache/symfony/tags/TRANSLATE
```

`cache:flush` had been run as `payless`, so the tag file was written
`payless:payless` mode 664. php-fpm runs as `www-data`, which is not in group
`payless`, so it could read but not write. `var/cache` also held 84 root-owned
files left by an earlier `sudo bin/magento` run.

Cleared without root — `var/cache` is 0777 with no sticky bit, so its contents
are removable by anyone, and `www-data` then recreates them as itself:

```bash
rm -rf var/cache/*
```

**This will keep recurring** while the CLI user and the web user write the same
tree with 664/775 modes. The durable fix needs root once:

```bash
sudo chown -R payless:www-data var generated pub/static pub/media app/etc
sudo find var generated pub/static -type d -exec chmod 2775 {} +   # setgid: new files inherit the group
sudo find var generated pub/static -type f -exec chmod 664 {} +
```

`generated/` currently holds **16,849 root-owned files**. In `production` mode
it is only read by the web user, so it is not breaking anything today, but it
will block the next CLI `setup:di:compile`.

### 3g. The JS break: Hyvä's `hyva` helper object stopped rendering

The CSS rebuild (3c) was necessary but was **not** the whole story. The
storefront's interactive UI was dead for a separate reason, visible only in the
browser console:

```
Hyvä helpers are not loaded yet. Make sure they are included before this script
Uncaught TypeError: hyva.alpineInitialized is not a function
Uncaught TypeError: hyva.str is not a function
Uncaught TypeError: hyva.createBooleanObject is not a function
Alpine Expression Error: eventListeners is not defined
```

Every Alpine component on the page (customer menu, compare link, cart drawer,
mobile menu) throws, because they all call `hyva.*` helpers.

**Cause.** Hyvä's 13 KB JS helper (`Hyva_Theme::page/js/hyva.phtml`) is
attached to the `head.additional` element by
`magento2-theme-module/src/view/frontend/layout/default_hyva.xml`:

```xml
<referenceContainer name="head.additional">
    <block name="head.js" template="Hyva_Theme::page/js/variables.phtml"/>
    <block name="head.hyva-scripts" template="Hyva_Theme::page/js/hyva.phtml"/>
</referenceContainer>
```

But `head.additional` is declared as a **block**, not a container, in
`magento2-default-theme/Magento_Theme/layout/default.xml`. After the upgrade
that element no longer resolves, so *nothing* attaches to it and
`Magento\Framework\View\Result\Page::render()` renders it as nothing:

```php
$addBlock = $this->getLayout()->getBlock('head.additional');
'headAdditional' => $addBlock ? $addBlock->toHtml() : null,
```

Measured against the pre-upgrade capture:

| | pre-upgrade | after upgrade |
|---|---|---|
| scripts touching `window.hyva` | 3 (incl. one **13,478 B**) | 1 (1,837 B — cookies only) |
| `<meta>` tags | 20 | 7 |
| `og:` tags | 6 | **0** |
| `twitter:` tags | 7 | **0** |

The lost meta tags are the same defect: `Mageside_Recipe` attaches its
`social_metadata` block to `head.additional` with `<referenceContainer>` too.

Ruled out along the way: it is **not** CSP (only
`Content-Security-Policy-Report-Only` is ever sent — it logs, it never
blocks); not the `hyva-themes.json` registry (regenerated and correct); not
the base-layout resets (`hyva:base-layout-resets:info` reports
`Hyva/default` "Already using the generated base layout", and regenerating
changed nothing); and not caused by the Font Awesome edit — the meta-tag loss
is already present in a page captured before that edit.

**Fix.** `app/design/frontend/Aureate/hyva/Hyva_Theme/layout/default_hyva.xml`
re-attaches the helper to `before.body.end`, which does resolve (alpine,
cookies and private-content all render from it), with `before="-"` so `hyva`
is defined before Alpine boots and before `cookies.phtml` /
`private-content.phtml` call `hyva.alpineInitialized()`. Verified: the helper
renders exactly once per page, ahead of `alpine3.min.js`, and
`alpineInitialized`, `createBooleanObject`, `str`, `formatPrice`, `getCookie`,
`getFormKey` and `getBrowserStorage` are all defined.

**Still broken by this defect: the Open Graph and Twitter meta tags.** They
must live in `<head>`, so the `before.body.end` workaround cannot carry them.
That is SEO-only — no visual or functional impact — and the proper resolution
is upstream: `head.additional` needs to be a container, or Hyvä needs to
attach to it with `referenceBlock`. Worth raising with Hyvä support, since the
licence is paid.

### 3h. Header icons rendered as empty white boxes

**Symptom.** The search, account and cart buttons showed as blank white
squares with a drop shadow. The cart count badge still showed.

**Cause.** 1.5.2 swapped the header's Heroicons for Lucide icons and gave the
buttons `class="btn bg-transparent border-transparent p-1"`. The SVGs rendered
correctly (`stroke="currentColor"`), but this child theme's `.btn`
(`web/tailwind/components/button.css`) is still the 1.3.9 solid button:
`text-white shadow-md`. `bg-transparent` removed the fill, not the white text,
so the icons were drawn white on the white header. 1.5.2's own `.btn` is a
Tailwind v4 component with inherited dark text, which this v3 build does not
use.

The same markup is used by the compare, wishlist and mobile-menu toggles and
by the close buttons in the cart drawer and login popup.

**Fix.** Two child-theme changes, then a CSS rebuild:

- `web/tailwind/theme/components/header.css` restores the 1.3.9 icon-button
  look (inherited colour, no shadow, `rounded`, `hover:bg-primary/10`, and a
  `focus-visible` ring instead of the old ring on every click). It matches
  `[class~="btn"][class~="bg-transparent"][class~="border-transparent"]`. It
  uses attribute selectors rather than `.btn` because Tailwind v3 copies any
  rule containing `.btn` into each `@apply btn` (see the note in
  `product-list.css`). Requiring `border-transparent` keeps the rule off the
  cart drawer's own `btn bg-transparent text-slate-900` buttons.
- `tailwind.config.js` adds `textColor['on-primary']` (white). 1.5.2's header
  badges use `text-on-primary`, which this config never generated. The badge
  number only looked white because it inherited `.btn`'s white text, so without
  this it would have turned dark once the button colour was fixed.

`.btn` itself was not changed; a site-wide change would restyle every other
button.

```bash
cd app/design/frontend/Aureate/hyva/web/tailwind && npm run build
cd -   # back to the project root
rm -rf var/view_preprocessed/* pub/static/frontend/Aureate/hyva
php bin/magento setup:static-content:deploy -f --theme Aureate/hyva en_US
rm -rf var/cache/* var/page_cache/*     # not cache:flush — see 3f
```

**Verified.** A rule-by-rule diff of `styles.css` before and after shows 5 rules
added, 0 removed (the 4 header rules plus `.text-on-primary`). No copies were
cloned into `@apply btn` consumers. The deployed file is byte-identical to the
build.
